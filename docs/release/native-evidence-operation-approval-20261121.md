別端末・別保管先への変更や権限・認証情報の追加は、別途対象を提示する。

## 本人の指定が必要な情報

1. **鍵管理端末／実行先**: 端末の識別名と、既存の利用可能な接続方法。
2. **旧鍵・旧証跡の所在**: その端末に存在するか、別の保管先か。鍵本文や
   パスフレーズは不要。詳細な私有パスは公開PR・Issueへ記録しない。
3. **新旧鍵と証跡の保管先・バックアップ先**: 利用する既存の暗号化保管領域の指定。
   新サービスの契約や外部ストレージの作成は、この案に含めない。

上記を指定し、運用案を承認するか、変更したい条件を回答してもらう。
現在の公開情報から実際の旧鍵保有・復元可能性を確定することはできない。

## 実施順序と受入記録

1. 旧鍵の存在・所有者・権限、既存証跡と独立したhash記録を私有環境で確認する。
   不足があれば発行・切替を進めず、復旧または受入条件の変更を本人へ提示する。
2. 承認された領域に新鍵・証明書を発行する。公開するのは証明書、公開鍵の識別情報、
   有効期間、固定の検証結果のみとする。バックアップからの復元も確認する。
3. `verify_evidence_rotation.py`で、旧証跡hash・旧鍵復号・平文hash、新鍵との不一致、
   新証明書と新鍵の一致、新鍵の暗号化／復号を検証する。
   旧証跡の平文hashが当時記録されていない場合は、当時の受入記録との
   receipt単位照合へ変更する承認を求め、同一バイト列の確認済みとは書かない。
4. 候補PEM、S04のpin、固定WAL後継版のPEM・ref・pin、関連source/config hashを
   一組のレビュー対象として提出する。元の固定commitを変更・上書きしない。
5. 正確な更新commitで、既存の容量・隔離・回収条件を維持したbounded smokeを実施。
   新しい実証跡を私有環境で復号し、receiptとrun/sourceを照合する。
6. 候補への統合と、default branchへの監視配置を承認対象として提示する。
   監視の正常系と期限不足の失敗系、本人への通知到達を確認する。
   default branchに配置するまでscheduleは稼働しない。
7. 証跡原本と対応表を指定保管先へ回収し、旧鍵・新鍵の復元を確認する。
   Issue #690には公開可能な結果・commit・run・期限のみを、承認後に追記する。
8. すべての受入結果が揃ってから「ローテーション・恒久運用導入完了」と記録する。
   リリース全体の他の受入条件はそれぞれ維持する。

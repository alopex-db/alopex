## Compatibility and distribution — to finalize

The #740 migration changes the Arrow Rust types exposed by DataFrame and
embedded APIs from Arrow 53 to Arrow 60. Rust applications exchanging those
types must align their Arrow dependencies. This is a Rust source migration,
not a database/WAL format change. Old-data and Python compatibility must still
be verified against the final candidate before release acceptance.

Final qualification must exercise supported legacy database and WAL inputs.
Direct database upgrade and external export/import are separate contracts;
Rust source compatibility is also distinct from runtime file compatibility.
Migration cannot recover information already lost by an older export.

The [Rust configuration policy](../rust-config-compatibility.md) preserves the
six-field `EmbeddedConfig` API published in 0.8.16 and extends private-field
`DatabaseOptions`. Unchanged four-field literals from 0.8.15 still require the
documented constructor migration; this is not full source compatibility with
those literals. Compile-only evidence records supported and known-incompatible
clients separately from runtime upgrade checks.

The [CSV NULL policy](../csv-null-compatibility.md) distinguishes unquoted `\N`
from quoted marker text and preserves empty TEXT, quoted NULL words and TEXT
whitespace. Old ambiguous CSV files require re-export from the original data;
the new reader cannot recover a distinction already lost by the old writer.

The [columnar export policy](../columnar-export.md) describes storage-aware
CSV/Parquet exports, file failure handling, and the narrowly verified SELECT
workaround for older published binaries. Already-empty exports cannot restore
the source rows. The [VECTOR Parquet policy](../vector-parquet.md) defines #693's
List<Float32> output, supported list inputs, finite-value/NULL/precision rules,
and explicit recreation of dimension, metric and indexes. Its implementation is
in the candidate and still awaits final candidate/package acceptance.

The [HNSW TRUNCATE policy](../hnsw-truncate-compatibility.md) describes the #677
transaction fix and rebuilding an already affected index from intact table
rows. Reopening alone does not repair old persisted graphs. The fix was
integrated into the v0.8.17 candidate in #705 and individually accepted for
#677. Final RC package verification remains tracked in #690.

The [KV scan pagination policy](../kv-scan-pagination.md) describes byte-bounded
prefix/range pages, scoped Python cursors and cooperative async collection for
#678. Integration and acceptance remain tracked in #690.

The [WAL capacity checkpoint policy](../wal-capacity-checkpoint.md) describes
#683's bounded pre-append reclamation, snapshot retention, I/O failure behavior,
capacity errors and manual measurement procedure. Oversized atomic batches
remain owned by #682. Integration and acceptance remain tracked in #690.

### Oversized atomic WAL transactions

The [overflow format and recovery contract](../wal-overflow-format.md) describes
the explicit opt-in for Rust and Python, including SQL transactions. Ordinary
non-overflow opens retain the legacy format. Enabling overflow activates a WAL
v3/container reader requirement: older software must reject the upgraded store,
and there is no downgrade of a store containing new committed references.
Reopening requires the overflow opt-in again. Do not enable it on a store that
must remain readable by an older Alopex binary.

The whole transaction remains atomic; it is not silently split into commits.
Transaction bytes, retained write-set memory, fragment buffers and spool disk
usage have separate finite budgets. Exceeding a budget returns the dedicated
capacity error (`ALOPEX-S004` in SQL/Python). Rust callers exhaustively matching
the core `Error` enum need a `WalCapacityExceeded` arm; its diagnostic reason is
not a machine-readable contract. Actual filesystem failures remain I/O errors.
The logical accounting limits do not promise a whole-process RSS cap.
Uncertain reference I/O stops further
mutation on that writer until recovery/reopen determines the committed state.

The public Windows path uses the existing file/directory publication pipeline.
Controlled public-API errors, process exits and old-reader rejection have
[source-bound Windows evidence](../windows-overflow-acceptance.md). That evidence
does not establish physical-device power-loss behavior or qualify the final
release packages; both remain separate from the ordinary CI results.

Linux x86_64, Windows x86_64 and Apple Silicon remain the intended required
release targets. [Optional Intel delivery](optional-intel-parser.md) is implemented
in #794 through #764–#766 and requires separate native qualification. The historical
four-CLI expectation in #688 is interpreted with #686's adopted target policy:
Core Latest must retain all required CLI assets, and Intel availability is explicit.
Neither implementation nor local workflow tests establish published availability.
